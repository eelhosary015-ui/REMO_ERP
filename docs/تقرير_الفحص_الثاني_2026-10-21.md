## 3) المشاكل الحرجة (5)

### C-01 — أي حساب موظف يتجاوز فحص الصلاحيات بالكامل
- **الملف:** `server.ts:510-527`
- **المكوّن:** `globalApiSecurityMiddleware`
- **الوصف:** عند وجود `role === "employee"` أو `employee_id` في التوكن، يُعاد `next()` فورًا مع صلاحيات واسعة مضمّنة في الكود: `{ hr: true, "hr.read": true, attendance: true, payroll: true }` — **قبل** أي فحص صلاحيات وقبل تقييد الفرع.
- **الدليل (تحقّقتُ منه بنفسي):**
```ts
510  if (tokenPayload.role === "employee" || tokenPayload.employee_id) {
518    const empUser: ApiUser = {
523      permissions: { hr: true, "hr.read": true, attendance: true, payroll: true }
525    req.user = empUser;
527    return next();          // ← خروج قبل فحص الصلاحيات
```
- **الأثر:** أي موظف يملك حسابًا يستطيع قراءة مسيرات المرتبات وصرفها/إقفالها، وتعديل بيانات HR خارج نطاق فرعه.
- **اقتراح الإصلاح:** تمرير طلب الموظف على نفس محرك الصلاحيات (`hasPermission`) بمجموعة محدودة (بصمة/حضور فقط)، وعدم منح `payroll` افتراضيًا، وتطبيق فلتر الفرع.

---

### C-02 — نقطة نهاية «تعيين متقدم كموظف» عامة بلا مصادقة
- **الملفات:** `server.ts:311` + `modules/hr/hr_api.routes.ts:9445`
- **الدليل:**
```ts
311  if (pathname.startsWith("/api/hr/applications") && method === "POST") return true;
```
`startsWith` يجعل **كل** POST تحت `/api/hr/applications` عامًا، بما فيه `/:id/hire-to-employee` الذي يُدرج موظفًا جديدًا (براتب `basic_salary` مأخوذ من جسم الطلب).
- **الأثر:** أي شخص على الشبكة يستطيع إنشاء موظفين بأي راتب دون تسجيل دخول.
- **اقتراح:** تضييق الشرط إلى `pathname === "/api/hr/applications"` فقط، وإخراج `hire-to-employee` من القائمة العامة.

---

### C-03 — إلغاء سند خزينة لا يعكس قيده في دفتر الأستاذ
- **الملف:** `modules/accounting/treasury_api.routes.ts:1378-1393`
- **المسار:** `POST /api/treasury/transactions/:id/cancel`
- **الوصف:** يُنفَّذ `COMMIT` للخزينة أولًا، ثم يُبحث عن القيد بـ`source_type='supplier_payment'` بينما سندات الخزينة تُرحَّل حاليًا بـ`source_type='treasury_voucher'` → لا يُعثر على القيد ولا يُعكس، والأخطاء تُبتلع في `catch` وتعود الاستجابة `success: true`.
- **الأثر:** المستند يُلغى من الخزينة ويبقى مرحّلًا في الأستاذ → فرق دائم وتضخم في المصروفات/المدفوعات.

---

### C-04 — ازدواج ترحيل سداد الموردين
- **الملفات:** `modules/accounts/services/auto-posting.service.ts:2700-2725` + `modules/accounting/treasury_api.routes.ts:859`
- **الوصف:** سند الصرف يُنشئ قيدًا بمفتاح `('treasury_voucher', treasury_tx.id)`، بينما محرّك «مزامنة الموردين» يبحث عن قيد بمفتاح `('supplier_payment', supplier_transactions.id)` — معرّفان من فضاءين مختلفين، فلا يتطابقان، فيُنشأ قيد ثانٍ لنفس الدفعة.
- **الأثر:** مدين الموردين ودائن الصندوق يتضاعفان عند تشغيل المزامنة.

---

### C-05 — اعتماد الهالك والتسويات لا يغيّر رصيد المخزون الحقيقي
- **الملفات:** `modules/warehouses/routes/wastage.routes.ts:164-180`، `modules/warehouses/routes/adjustments.routes.ts:177-190`
- **الدليل (تحقّقتُ منه بنفسي):**
```ts
164  const stockRes = await pool.query(`SELECT * FROM stock_balances WHERE warehouse_id = $1 AND product_id = $2`, ...)
170  UPDATE stock_balances SET quantity = quantity - $1 ...
```
بينما رصيد المخزون المعتمد في كل النظام (`moveStock`, البيع, التحويل, الإنتاج) هو **`inventory_items` بمفتاح `ingredient_id`**.
- **الأثر:** مستند هالك «معتمد» + قيد تكلفة + قيد محاسبي، **ورصيد المخزون كما هو**. أي جرد لاحق سيكشف فرقًا غير مبرَّر.

## 8) ما لم يمكن التحقق منه (شفافية)

- **استعلامات `information_schema` داخل الأطفال:** لم تتوفر لهم أداة تنفيذ، فاعتمدوا على لقطة `_audit/schema.json` + الفحص الساكن. لذلك كل ادعاء يخص **وجود جدول/عمود** صُنّف «احتمال» ما لم أتحقق منه بنفسي.
- **ما تحقّقتُ منه بنفسي مباشرة:** `server.ts:311`، `server.ts:510-527`، `wastage.routes.ts:164-179`، `Sales.tsx:1179-1186`، وفحوصات سلامة البيانات الـ12.
- **اختبارات الأحمال / التزامن:** لم تُنفَّذ.
- **اختبارات الواجهة (E2E):** لا توجد أدوات Playwright/Cypress في المشروع.
