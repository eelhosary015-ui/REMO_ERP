# تقرير فحص واختبار تقني شامل — REMO PRO ERP

**تاريخ الفحص:** 21 أكتوبر 2026
**نطاق الفحص:** الواجهة الأمامية (React/TypeScript) + الخلفية (Express/TypeScript) + مخطط قاعدة البيانات (PostgreSQL) + التكامل بين الموديولات
**نوع العمل:** فحص وتشخيص فقط — **لم يُعدَّل أي ملف مصدري ولم تُغيَّر أي بيانات إنتاجية**

## 0) ملخص تنفيذي

| المؤشر | النتيجة |
|---|---|
| فحص TypeScript (`tsc --noEmit`) | ✅ **0 أخطاء** |
| البناء الكامل (`vite build` + `esbuild server.ts`) | ✅ **نجح** — `dist/server.cjs` 4.4MB |
| ملفات الكود المفحوصة | **593** ملف TS/TSX + **16** ملف SQL |

#### ISSUE-01 — بوابة كلمات مرور ثابتة (Master Password) داخل تسجيل الدخول

| البند | التفاصيل |
|---|---|
| **الخطورة** | Critical |
| **الملف** | `modules/system/system_api.routes.ts` |
| **الأسطر** | **628–640** (داخل `router.post("/api/login")` — السطر 585) |
| **الدالة/API** | `POST /api/login` |

**الوصف:** بعد فشل التحقق العادي من `bcrypt.compareSync`، يوجد فرع يسمح بكلمات مرور ثابتة مكتوبة في الكود لأي مستخدم اسمه `admin` أو `elhosary` أو دوره `admin`، بل **ويعيد كتابة هاش كلمة المرور في قاعدة البيانات** إلى تلك الكلمة.

**الدليل (كود فعلي):**
```ts
628  let validPassword = bcrypt.compareSync(password, user.password);
629  if (!validPassword && (user.username === 'admin' || user.username === 'elhosary' || user.role === 'admin')) {
630    const allowedMaster = ['Admin@1234', 'admin@1234', '123456', '123456789', 'elhosary123'];
631    if (allowedMaster.includes(password)) {
632      validPassword = true;
634      const newHash = bcrypt.hashSync(password, 10);
635      await pool.query("UPDATE users SET password = $1 WHERE id = $2", [newHash, user.id]);
```

**خطوات إعادة الإنتاج:**
1. `POST /api/login` بجسم `{ "username": "admin", "password": "123456" }`.
2. النتيجة: استجابة 200 + توكن صالح بصلاحيات مدير.

**التأثير:** اختراق كامل للنظام بأي من 5 كلمات مرور شائعة؛ وأسوأ من ذلك أن الدخول يغيّر كلمة مرور المدير الحقيقية في القاعدة، فيُقفل المالك خارج نظامه.

**اقتراح الإصلاح (بدون تنفيذ):** حذف الفرع 629–640 بالكامل، والاعتماد على `bcrypt.compareSync` فقط. ونقل أي "استعادة طوارئ" إلى سكربت إداري يعمل على السيرفر مباشرة، لا عبر HTTP.

**اقتراح الإصلاح:** تطبيق `migrations/2026-10-19-period-closing-hardening.sql` على قاعدة التشغيل بعد نسخة احتياطية، مع اختبار التريجر على فترة مغلقة.

#### ISSUE-15 — سويت الاختبارات غير معزول (يعتمد على بيانات حقيقية)

| البند | التفاصيل |
|---|---|
| **الخطورة** | Medium |
| **الملفات** | `tests/behavior/*.test.ts` + `tests/helpers/testDb.ts` |
| **المكوّن** | بيئة الاختبار |

**الوصف:** السويت ينسخ قاعدة التشغيل إلى `<db>_test` ثم يشغّل الاختبارات عليها **بدون تهيئة (seed) ثابتة ولا تنظيف**.

**الدليل (نتائج فعلية):**

| البيئة | الناجح | الفاشل | متوقع فشله |
|---|---|---|---|
| قاعدة منسوخة من بيانات حقيقية | 57 | **20** | 2 |
| قاعدة **نظيفة** (سكيما فقط) | 45 | **32** | 2 |

أسباب الفشل المؤكدة:
- `PeriodLockError: لا يمكن ترحيل القيد بتاريخ 2026-07-15: الفترة المالية 07/2026 مغلقة` — الاختبارات تستخدم تواريخ ثابتة في يوليو، والقاعدة المنسوخة تُغلق يوليو.
- `Error: الفترة المالية 07/2026 مغلقة` — 12 اختبار مرتبات فشل لنفس السبب.
- `expect(map.accounts_receivable).toBeGreaterThan(0)` فشل لأن دليل الحسابات المنسوخ يحتوي 16 حسابًا بدل الدليل الجزئي المتوقع (`expected 1 to be 19`).

**التأثير:** لا يمكن الاعتماد على نتائج الاختبار كإشارة جودة — النتائج تتغيّر بتغيّر بيانات القاعدة، وقد تُخفي عيبًا حقيقيًا أو تُظهر عيبًا وهميًا.

**اقتراح الإصلاح:** إنشاء قاعدة اختبار من الصفر + seed ثابت (حسابات، فروع، فترات مفتوحة) + `beforeEach` يفرّغ الجداول، وعدم الاعتماد على `DATABASE_URL` الإنتاجي.

#### ISSUE-16 — اختلاف لغة الحالات (عربي/إنجليزي) يُفسد الفلاتر المحاسبية
